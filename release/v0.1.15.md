# Azdaja v0.1.15

Azdaja v0.1.15 fixes the cooperative Jcode hook gate so explicit activation is required before routing or restricting tool calls, while preserving bounded shell reads under a pending challenge and sharing the narrow-read budget correctly.

This release is published only after exact-head CI and source-install integrity validation, reviewed standalone asset promotion, immutable tag checks, and published-byte verification.

## Installation and activation

The public installer at https://azdaja.dev/install selects v0.1.15. Running it again upgrades the selected managed integrations as well as the command-line binary. Existing user-owned Jcode configuration is preserved.

Hooks are inactive unless the host process explicitly sets `AZDAJA_JCODE_ACTIVATION` to `request`, `session`, or `repository`. Loading a skill or mentioning Azdaja does not activate routing. With explicit activation, bounded reads retain their shared budget even when a broad-read challenge is pending. Reviewed locked Cargo packaging, install, and release-build commands remain available.

After publication, `release/verify-published-release.sh 0.1.15` downloads and verifies all five payloads plus checksums and provenance across the published channels. No unreleased repo-memory features are included in this patch.

## Repo-local memory for agent handoffs

Azdaja can keep explicitly authored decisions, observations, failures, hypotheses, and disagreements with the repository in `.azdaja`. Fresh agent processes can recall those notes from another subdirectory or another personal HOME without combining project notes with personal global memory.

Project memory is available by default inside a Git worktree when both `AZDAJA_PROJECT_MEMORY` and `AZDAJA_HOME` are unset. Availability does not mean automatic recording. The store is created by an explicit memory write, and its own `.gitignore` excludes its contents from ordinary Git staging.

- `AZDAJA_PROJECT_MEMORY=on` selects project memory and requires a Git worktree.
- `AZDAJA_PROJECT_MEMORY=off` refuses non-global memory operations.
- `AZDAJA_PROJECT_MEMORY=legacy` selects the previous personal, working-directory-scoped storage.
- An explicitly configured `AZDAJA_HOME` retains legacy routing unless project mode is explicitly selected.
- `--global` continues to select separate personal global memory. There is no automatic merge or migration.

Recall is deterministic lexical retrieval, not semantic confidence or a vote between agents. It returns manual provenance and bounded one-hop relationship context, including linked disagreements whose text does not match the query. Selection is capped at four primary matches and eight context records, with a 64 KiB serialized-output limit and explicit omission counts.

File tags are ordinary retrieval metadata, not a mirror of the code tree or automatically maintained rename links. No automatic transcript harvesting, model calls, embeddings, compression, synchronization, or Git publication is introduced by this memory feature. Notes remain untrusted evidence that must be checked against current source and tests.

## Installation and hook regression coverage

The source-install workflow is configured to register and explicitly run the two installed-artifact memory tests against the installed executable, with a guard against a zero-test green run. Its challenged handoff explicitly activates the intended session rather than assuming the inactive hook will reject a read.

The real local HTTP installer acceptance path now also verifies the installed payload's hash, cross-home project handoff, nonmatching disagreement context, disabled writes, personal-global separation with a positive control, relocation, refusal without rewriting a corrupt ledger, and recovery after restoring valid bytes.

A narrow hook command-policy change covers reviewed local Cargo packaging and installation forms while retaining blocked source reads and rejecting nearby unsafe command forms. This is not a general shell allowlist.

Memory readers no longer create a missing writer lock or initialize personal state during cold list/show operations. Existing writer locks are acquired read-only for shared coordination. Unsafe parent directories and lock files are refused without permission repair, while ledger content and relationship validation remain intact. Fresh-process regressions cover the actual `global.lock` path, clean refusal, and recovery.
